# Driver Feedback Frontend API Reference

**Service:** Eastern Risen Driver Feedback API  
**Contract version:** `0.1.0`  
**Reference status:** Derived from implemented backend routes and TypeBox schemas  
**Last verified:** 2026-07-25
**API prefix:** `/api/v1`  
**Local backend:** `http://localhost:3000`

## 1. Purpose and contract authority

This document is the frontend-oriented reference for the API currently implemented in this repository. It describes authentication, request/response conventions, endpoint availability, payload shapes, error handling, and frontend integration rules.

Contract authority, from highest to lowest:

1. Runtime OpenAPI generated by the backend.
2. Route and TypeBox schema definitions under `src/modules`.
3. This document.
4. Product requirements that describe future API capabilities.

Development documentation is available at `http://localhost:3000/docs` while the API is running. Frontend code should generate or validate types against the runtime OpenAPI contract where practical. Update this file when a route or schema changes.

## 2. Global conventions

### Base URL

Configure the frontend with a validated environment value, for example:

```text
NEXT_PUBLIC_API_BASE_URL=http://localhost:3000
```

Append the documented route path beginning with `/api/v1`. Avoid embedding environment-specific hostnames in components.

### Content type

Send JSON request bodies with:

```http
Content-Type: application/json
```

The default backend body limit is 1 MiB.

### Session credentials

Admin and driver APIs authenticate with an opaque HttpOnly session cookie. Browser calls to session-authenticated endpoints must include credentials:

```ts
fetch(url, {
  credentials: 'include',
});
```

JavaScript cannot and must not read, copy, or persist the session cookie.
Production cookies use `SameSite=None; Secure` to support a frontend and API on
different sites. Every session-authenticated cross-origin request still needs
`credentials: 'include'`.

### Passenger authorization

Passenger feedback endpoints use the one-time opaque token returned by the driver handoff endpoint:

```http
Authorization: Bearer <feedbackAccessToken>
```

Never put this token in a URL, application log, analytics event, or ordinary persistent state. An offline envelope may retain it only for the protected synchronization queue.

### CORS and origin protection

The frontend origin must exactly match an entry in the backend `FRONTEND_ORIGINS` allowlist. Credentialed CORS is enabled only for allowed origins. State-changing browser requests from other origins fail with `ORIGIN_NOT_ALLOWED`.

### Success envelopes

Single resources:

```ts
interface DataResponse<T> {
  data: T;
}
```

Paginated collections:

```ts
interface PaginatedResponse<T> {
  data: T[];
  pagination: {
    page: number;
    pageSize: number;
    total: number;
  };
}
```

All list endpoints use this pagination envelope. HTTP `204` has no response body.

### Error envelope

All documented errors use:

```ts
interface ApiErrorResponse {
  error: {
    code: string;
    message: string;
    details?: unknown;
    requestId: string;
  };
}
```

Every response includes the same correlation identifier in the `x-request-id` header. Show friendly, code-specific UI copy. Preserve `requestId` in technical details or support messaging.

### Time and identifiers

- Domain identifiers are UUID strings.
- API timestamps are ISO 8601 date-time strings.
- Render timestamps using the timezone returned by agency settings or endpoint
  metadata; the initialized default is `Asia/Kolkata`.
- Do not parse identifiers as numbers.

### Principal type

### Endpoint summary

| Method | Path | Auth | Success | Purpose |
| --- | --- | --- | --- | --- |
| `POST` | `/api/v1/auth/admin/login` | Public | `200` | Start an admin session |
| `POST` | `/api/v1/auth/driver/login` | Public | `200` | Start a driver session |
| `POST` | `/api/v1/auth/logout` | Cookie optional | `204` | Revoke the current session and clear cookie |

### Admin login

```ts

  email: string; // valid email, max 320
  password: string; // 1–128 characters
}
```

### Driver login

```ts
interface DriverLoginRequest {
  driverCode: string; // 1–64 characters
  password: string; // 1–128 characters
}
```

### Login response

```ts
interface LoginResponse {
  data: {
    user: Principal;
    expiresAt: string;
  };
}
```

`GET /auth/me` returns `{ data: { user: Principal } }`.

### Frontend behavior

- `AUTHENTICATION_FAILED`: keep the user on the login form and show a generic invalid-credentials message. The backend intentionally does not distinguish unknown, inactive, or bad-password accounts.
- `AUTHENTICATION_REQUIRED`: clear private in-memory/cache state and redirect to the appropriate sign-in screen.
- `ADMIN_ACCESS_REQUIRED` or `DRIVER_ACCESS_REQUIRED`: show a safe forbidden state or redirect to the principal's own home.
- Do not infer authorization only from hidden navigation; the server guard remains authoritative.

Driver employment and assignment fields in `DriverProfile` are read-only.

`CURRENT_PASSWORD_INVALID`, and `PASSWORD_REUSE_NOT_ALLOWED`.

outsourced driver also requires an active vendor.

### Replacing draft questions

```ts
interface OptionInput {
  valueKey: string; // 1–100, /^[a-z0-9_-]+$/
  label: string; // 1–200
  scoreValue?: number | null;
}

interface QuestionInput {
  stableKey: string; // 1–100, /^[a-z0-9_-]+$/
  prompt: string; // 1–1000
  questionType: QuestionType;
  category: QuestionCategory;
  status?: QuestionStatus; // defaults to ACTIVE
  isRequired: boolean;
  contributesToScore: boolean;
  scoreMin?: number | null;
  scoreMax?: number | null;
  options?: OptionInput[]; // max 100; omitted values are stored as []
}

interface ReplaceQuestionsRequest {
  questions: QuestionInput[]; // max 100; array order becomes displayOrder
}
```

`PUT` replaces the entire ordered question collection. The frontend must send every intended question, not only changed rows. Only a `DRAFT` version is mutable.

Question validation rules:

- Stable question keys must be unique within the version.
- Option keys must be unique within a question.
- Drafts may be saved with incomplete option and score configuration so the editor can persist
  incremental changes.
- On publish, `EMOJI_RATING`, `YES_NO`, `SINGLE_CHOICE`, and `MULTIPLE_CHOICE` require at least
  two options.
- `STAR_RATING` and `TEXT` do not allow options.
- A scored star question needs valid `scoreMin` and `scoreMax` bounds.
- On publish, a scored option question requires a numeric `scoreValue` for every option. Scores
  remain optional when `contributesToScore` is `false`.
- An active publish must contain at least one active question.
- `TEXT` is stored as not contributing to score.

Persist `data.questionnaire` exactly as received for submission and offline retry. Do not add, remove, sort, or transform fields in the submitted `questionnaireSnapshot`.

### Answer values

Submit one answer per answered question:

```ts
interface FeedbackAnswer {
  questionId: string;
  value:
    | number       // STAR_RATING, within scoreMin/scoreMax
    | string       // EMOJI_RATING or SINGLE_CHOICE valueKey; TEXT content
    | boolean      // YES_NO
    | string[];    // MULTIPLE_CHOICE valueKeys, non-empty and unique
}
```

Optional unanswered questions should be omitted from `answers`; do not submit empty strings or empty arrays. Every required active question must appear exactly once.

### Submission request

```ts
interface SubmitFeedbackRequest {
  clientSubmissionId: string; // UUID generated once before first attempt
  questionnaireVersionId: string;
  questionnaireSnapshot: PassengerContext['questionnaire'];
  respondent: {
    name: string; // 1–200
    phone: string; // 1–32
    email: string; // valid email, max 320
    bookingReference: string; // 1–100, must match trip ignoring case/outer whitespace
    consentAccepted: true;
    consentedAt: string;
  };
  answers: FeedbackAnswer[]; // max 100
  submittedAt: string;
  submissionMode: SubmissionMode;
}
```

### Submission receipt

```ts
interface SubmissionReceipt {
  data: {
    id: string;
    clientSubmissionId: string;
    tripId: string;
    receivedAt: string;
    submissionMode: SubmissionMode;
    replayed: boolean;
    rewardEligible: boolean;
  };
}
```

New acceptance returns `201` and `replayed: false`. Repeating the same accepted `clientSubmissionId` for the same trip returns `200` and `replayed: true`. Both are successful terminal outcomes.

### Offline integration rules

- Generate `clientSubmissionId` before the first connected attempt and never replace it for retries.
- Preserve the exact request envelope needed for synchronization.
- Use `ONLINE` for the initial connected attempt and `OFFLINE_SYNC` when replaying a locally queued submission.
- Queue only a known offline state or retryable transport/service failure.
- Remove local payload only after `201` acceptance or `200` idempotent replay.
- `OFFLINE_SYNC` receipts are always `rewardEligible: false`.
- Do not offer a reward while offline or for queued submissions.

Relevant errors: `FEEDBACK_HANDOFF_INVALID`, `CLIENT_SUBMISSION_ID_CONFLICT`, `TRIP_FEEDBACK_ALREADY_SUBMITTED`, `QUESTIONNAIRE_VERSION_INVALID`, `BOOKING_REFERENCE_MISMATCH`, `QUESTIONNAIRE_SNAPSHOT_INVALID`, `FEEDBACK_ANSWERS_INVALID`, `TRIP_FEEDBACK_STATE_CONFLICT`, `TRIP_NOT_FOUND`.

The passenger context also returns completion copy:

```ts

```

Render this server-provided thank-you message on the safe completion/hand-back
screen. Do not hard-code the agency timezone or completion copy.

## 15. Error handling reference

### Global/system errors

| HTTP | Code | Frontend handling |
| --- | --- | --- |
| `400` | `REQUEST_VALIDATION_FAILED` | Map validation details to fields when safe; otherwise show form summary |
| `401` | `AUTHENTICATION_REQUIRED` | Clear private session state and return to role login |
| `401` | `AUTHENTICATION_FAILED` | Generic invalid-credentials message |
| `403` | `ADMIN_ACCESS_REQUIRED` | Safe admin-forbidden state |
| `403` | `DRIVER_ACCESS_REQUIRED` | Safe driver-forbidden state |
| `403` | `ORIGIN_NOT_ALLOWED` | Configuration error; do not retry automatically |
| `404` | `ROUTE_NOT_FOUND` | Developer/configuration error for known frontend routes |
| `413` | `REQUEST_BODY_TOO_LARGE` | Do not retry unchanged payload |
| `415` | `UNSUPPORTED_MEDIA_TYPE` | Client defect; verify JSON header/body |
| `429` | `RATE_LIMIT_EXCEEDED` | Temporarily disable/retry with backoff; retain safe form state |
| `500` | `INTERNAL_SERVER_ERROR` | Recoverable page error; show request ID and controlled retry |

### Retry classification

Safe automatic retries generally include loss of connectivity, DNS/transport failure, request timeout where no domain response was received, and selected `5xx` responses with bounded exponential backoff.

Do not automatically retry unchanged `400`, `401`, `403`, `404`, `409`, `413`, or `415` responses. Handle `429` using backoff and any future `Retry-After` header. For passenger feedback, domain errors must never be converted into offline queue success.

## 16. Frontend client requirements

The typed client layer should:

1. keep session-cookie and passenger-token authorization explicit;
2. add `credentials: 'include'` for session calls;
3. add JSON headers only when a body exists;
4. parse `204` without calling `response.json()`;
5. parse success and error envelopes once;
6. preserve HTTP status, error code, details, and request ID;
7. support abort signals and bounded timeouts;
8. distinguish transport, protocol, authentication, validation, conflict, and server errors;
9. never log request bodies or authorization values from sensitive routes;
10. invalidate/refetch affected list/detail queries after mutations.

Prefer types generated from OpenAPI. If handwritten types are temporarily necessary, isolate them in one contract module and add contract tests so drift is detected.

## 17. Known API gaps

The product specification describes the following frontend capabilities, but the routes are not implemented as of the verification date:

- rewards, prize inventory, wheel attempt/outcome, and reward email state;
- reports and CSV/Excel/PDF exports;
- pending synchronization server status;
- dedicated vendor detail reads;
- restore operations for archived records.

The frontend must not invent production endpoints or show false mutation success. Use explicit feature gating or documented placeholders until a backend contract exists.
